## 2. Purpose and users

The administrator's question is “Who is on the team, which tools can they use, and what do I need to change?” A production call sheet answers through complete ruled person records, a cumulative-plan annotation rail and a grouped permission sheet. Pictures' ring-and-dot mark and the copper inflatable seam connect the screen to Sempertex installations.

Invited external people activate personal access, accept the notice and reach the first permitted tool. Signed-in people identify their account, change their own password and sign out. Account administrators (`cuentas.administrar`) invite/search/manage people; role administrators (`roles.administrar`) inspect system roles and manage custom ones. Those permissions are independent; do not grant access merely from a visible role name or `internas.usar`. A person without permission sees a scoped refusal and safe exits without restricted data.

Success is a confirmed account/access change and a clear next destination, not a fabricated local success. All people, companies, emails, timestamps and counts in the HTML are illustrative. Reserved `.example` addresses and links do not issue real accounts. The header's David identity is the same as Mi cuenta; the activation example identifies Valentina Rojas. The footer visibly labels simulated data and operations.

## 3. Information architecture and hierarchy

Preserve the selected composition: broad Pictures/Sempertex masthead → asymmetric running head with condensed display title and edition/count cell → neutral horizontal Cuentas / Roles y permisos / Mi cuenta navigation where permitted → paper workspace plus narrow plan rail → aligned footer. The working paper is the largest content block. No dashboard-card grid, sidebar or unrelated spend analytics replaces this hierarchy.

Accounts paper order: “Registro de acceso” and “Invitar persona” → name/email search and role/state filters → complete ruled account records → visible filtered/total count and Bogotá-time caption. Every record keeps identity, company, one assigned role, status, last access and “Gestionar” together. Total and result count derive from the same rows; loading/failed reads must not imply an authoritative zero.

Roles paper order: heading and “Crear rol” → selectable role list beside selected-role editor → system/read-only or custom/name explanation → four tool groups with labeled permission choices → custom save/delete actions and feedback. System choices and custom roles share the list without hiding the five required system roles. The plan rail remains supporting information, never a second navigation system.

Public and own-account forms share the paper's left axis and a 620px form-body maximum. Activation places invited identity before passwords, full notice before unchecked consent, and consent before activation. Mandatory notice reacceptance withholds all other product navigation; sign-out remains reachable. Dialogs disclose contextual invitation, management, one-time link and permanent deletion without moving those repeated tasks onto a new dashboard.

## 6. Flows

**F1 — Sign in.** Enter invited email/password → submit once → loading → server-confirmed safe destination. Wrong password, unknown email, deactivated account and locked email use the same refusal: “No pudimos iniciar sesión. Revisa el correo y la contraseña. Después de varios intentos fallidos debes esperar quince minutos.” English: “We could not sign you in. Check your email and password. After several failed attempts you must wait fifteen minutes.” Do not expose existence/state/attempt counters. SP-1 locks an email after five failures in fifteen minutes for fifteen minutes; the UI always supplies the neutral hint. Invitation-only copy and administrator-issued recovery are visible; no open registration or automatic email reset. Sessions last 30 days under SP-1 and end on sign-out/deactivation/password change as specified below.

**F2 — Activate.** Validate the invitation without consuming it on load → display invited name/email → new password and confirmation → full current notice in browser/selected language → unchecked consent → Activate disabled until checked → explicit valid submission. Password is 8–200 characters, confirmation equal; allow password-manager/paste. Only confirmed activation stores notice version/date, consumes the one-use seven-day token, creates a session and opens the first allowed tool or Mi cuenta. Expired, used or replaced links use one generic `LINK_INVALIDO` recovery, hide password entry and ask the administrator for a new link; do not disclose which condition or recipient data from an invalid link. The fixture's Chat destination is an example for its plan, not a destination forced on all roles.

**F3 — Invite.** Cuentas → Invitar persona → required name/email, optional company, exactly one role/plan → Generar invitación → pending → server-confirmed one-time link receipt. Registered email returns `CORREO_REGISTRADO` and “Este correo ya está registrado. Gestiona su cuenta existente.” without creating another invitation. Receipt names recipient, one-use/lifetime and manual sharing; nothing claims email delivery. Copy reports success only after clipboard success; failure instructs selecting/copying the wrapping link manually. Closing/leaving removes the receipt. Generate a new invitation from an invited account's management dialog to recover a lost/expired receipt; explain before generation and on receipt that all older unused invitations for that account become invalid. Reset and invitation kinds do not cross-revoke.

**F4 — Administrator reset.** Manage an existing account → Generar restablecimiento → explain older unused resets become invalid, new link is single-use for 24 hours → generate/copy/close once. Recipient opens V3 → new password twice, 8–200 and matching → confirmed reset revokes sessions → sign in with the new password. No repeated notice consent is added to reset; invalid link recovery matches F2. Generating a reset does not itself assert that a password was changed.

**F5 — Account administration.** Search name/email and filter role/state → Manage selected row → read identity and choose one role → Guardar rol; effects apply next request. Deactivate ends sessions and preserves saved work; Reactivate restores access subject to the same role and notice. Last active Administrator cannot be deactivated/deleted/demoted (`ULTIMO_ADMIN`); fixture David is the last administrator, not a rule that all administrators are immutable. Saved projects/decorations or any registered saved-work row block deletion (`CUENTA_CON_TRABAJO`) and change nothing; explain deactivation as the alternative. Spend alone is not saved work. Only a work-free account can proceed to permanent-delete AlertDialog; require exact matching email, explain irreversibility and retention of anonymous spend as “Cuenta eliminada”. Unknown/stale eligibility never enables deletion; recheck on confirm. Handle a concurrent refusal in place with refreshed authoritative data and no success claim. Profile editing, bulk operations and account transfer are outside scope.

**F6 — Roles and plans.** Select one of five system roles to inspect its read-only permissions → or Crear rol → name and initially unselected independent checkboxes grouped by tool → require at least one permission (`ROL_SIN_PERMISOS`) → Save confirmed custom role. Editing loads that role's actual selected permissions; it never inherits another role's transient checkbox state. System roles cannot be edited/deleted (`ROL_SISTEMA`). Assigned custom roles refuse deletion (`ROL_EN_USO`) and explain assigning another role first; unassigned custom roles use permanent-delete confirmation. The displayed assigned count must come from real account assignments, not list position. No separate additive plan field exists: access plans are roles, one role per account.

**F7 — Own password.** Account disclosure → Mi cuenta → read own identity/company/role and notice version/date → enter current password, new password and confirmation → validate → confirm service success. Wrong current password is actionable without ending the valid session. The service ends all old sessions and T2.2 opens a new one for the requesting browser; clear secret fields and announce “Contraseña cambiada. Esta sesión se renovó; tus otras sesiones terminaron.” The person remains signed in here; other browsers must sign in again. This is distinct from F4 reset. No self-editing of email/profile/role is introduced.

**F8 — Notice update.** On next request after a notice version change, replace requested content with V7 → show full displayed version and unchecked consent → accept and store exactly that version/date → permitted destination, or sign out to V1. No skip/later or underlying product links before consent. If displayed version changes while open, discard acceptance of the old text and ask for fresh consent. Failure/offline retains input for that version with explicit retry and no recorded-success fiction. The v1 body in the preview is an illustrative reacceptance scenario, not a newly invented v2 legal text.

## 8. States
