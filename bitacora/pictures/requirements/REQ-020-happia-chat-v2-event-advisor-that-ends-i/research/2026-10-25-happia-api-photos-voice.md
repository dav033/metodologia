## 1. Happia API structure

Auth and routes. The worktree config requires HAPPIA_API_BASE_URL and HAPPIA_API_KEY (packages/happie-package-ia/src/config.ts:6-17). Both client and live curl probes used the x-api-key header (cliente.ts:153-159). The base resolved to https://www.happia.co/api. GET /services and /packages returned JSON envelopes {status,data,pagination}; pagination has integer totalItems, totalPages, currentPage. page and limit are accepted; city is also passed by our client as an optional city slug (cliente.ts:113-124). Live service limits: limit=500 returned 200 and 501 returned 400. Package limit=101 returned 400. The client caps both at 100 and reads at 100 per page, with pagination and a bounded full-read loop (cliente.ts:12-27, 69-110); that cap is conservative for services and matches the tested package limit. Both resources also accepted city=barranquilla (200); the probe did not count those filtered results.

Live counts at limit=100: 57 services (1 page) and 18 packages (1 page). page=1 and page=2 with limit=2 returned the expected currentPage and totalPages (29 services, 9 packages). GET / returned 308 to /api/; /openapi.json, /docs, /themes, /categories, /products, /venues, /cities, /carts, /cart, /themed-items, /event-types, and /venue-types returned 404. Thus the checked API exposes no venue, theme, event-type, or cart resource. This is an observed endpoint-surface result, not proof that Happia has no private/unlisted API.

## 2. Photo detection and brief flow

Upload and storage. POST /api/asesor/photos authenticates the advisor role, enforces same-origin, limits one turn to four photos, each at most 6 MiB, and accepts only kind=inspiration|venue (src/app/api/asesor/photos/route.ts:7-14, 40-62, 77-89). prepareAdvisorPhoto accepts JPEG/PNG/WebP, verifies the decoded format and dimensions, rejects images over 40 megapixels, and creates a rotated, max-1800px, JPEG quality-90 derivative while retaining original bytes (src/lib/asesor/photos.ts:4-47). The route stores originals as Buffer attachments. The initial attachments table stores data BYTEA; migration 002 adds photo_kind (inspiration/venue), nullable confirmed boolean, and preference (like/dislike/neutral) (scripts/migrations-asesor/001_initial.sql:32-40; 002_photo_metadata.sql:1-7). Upload defaults to confirmed=null and preference=neutral (photos/route.ts:86; repository.ts:147-152).

Model and first look. On the chat turn, agent.ts rebuilds stored conversation history, appends attachment kind/feedback notes, and attaches the actual images only for the latest user message; it re-encodes the derivative as JPEG/base64 and asks the model to describe each photo in its first answer (src/lib/asesor/agent.ts:28-46). That first look is ordinary streamed assistant prose. There is no structured vision response schema or persisted analysis object in this path. The only structured photo tool is record_photo_feedback, taking attachmentId, confirmed, preference (src/lib/asesor/tools.ts:18, 33-40). It verifies that the ID belongs to this conversation, then writes those two feedback values to the attachment (tools.ts:258-276; conversar/route.ts:97-112). The server does not independently check that the customer explicitly said the model’s per-photo reading was correct or that a particular like/dislike was expressed; this is currently a prompt/model convention, not a deterministic check.

Brief output. EventBrief already has budget+currency, organiserPriority (impress/personalise/simple/best_price), style, theme, colors, likes/dislikes and notes (src/lib/asesor/contracts.ts:23-37). Brief state is versioned JSONB and each changed state is inserted as a new version (repository.ts:217-255), but the public brief loader reads only latestBrief; the brief response carries a single summary version, not a change-history timeline (repository.ts:258-265; src/lib/asesor/brief.ts:89-105, 108-132). The brief includes photos only as generated thumbnail URLs plus id, MIME type, kind, confirmed and preference. It carries no first-look prose/structured style read and no per-photo “what to keep” details (brief.ts:5-13, 123-131).

Existing structured photo analysis. Yes, the repo has useful foundations. POST /api/references/analyze runs the reference-analysis pipeline and returns a structured blueprint, element appearances, observed colors and optional pixel-measured color analysis (src/app/api/references/analyze/route.ts:80-87, 111-130, 161-215; src/lib/ia/amaterasu/analizar-referencias-v2.ts:515-548). Its fixed reader model is gemini-3.6-flash (src/lib/ia/amaterasu/config-lectura-foto.ts:1-20). Separately, globos3d/lectura-foto.ts defines a strict Gemini JSON schema for named colors with hex/weight/finish and element-level geometry (lines 22-40, 166-180). This proves structured style/colors/elements are feasible, but these readers target decoration reconstruction/balloons; they do not directly return a customer-oriented overall style + palette + “keep” checklist. Reusing them would require an adapter/contract and explicit storage/projection into the advisor brief; a focused new schema may be smaller and less coupled than the geometry-heavy reader.

Gaps and defects surfaced: first look is untyped prose and can’t be reliably rendered or compared; no per-photo keep list or customer-approved analysis is stored; model tool calls can persist unsupported photo feedback without server-side evidence in the customer turn; “search Happia venue” has no venue endpoint; services/images are fetched but do not inform this package proposal. Existing brief versions can support history, but the brief projection does not expose prior versions/diffs.

## 3. Voice service and deployment

Code contract: browser dictation is enabled from GET /api/voz/transcribir; this route requires an authenticated session and same-origin request (src/app/api/voz/transcribir/route.ts:16-20; src/lib/voz/transcribir.ts:55-60). POST validates the audio, enforces a 2 MiB byte cap and 60-second duration cap, rate limits per IP (12/minute, 200/hour in process memory), and forwards it to VOZ_URL/v1/transcribir with an HMAC timestamp/signature. The service call has 20-second per-attempt and 30-second total budgets, with one bounded retry on 503 (src/lib/voz/limites.ts:1-15; src/lib/voz/cliente-vps.ts:5-11, 61-109; src/lib/voz/firma.ts:3-9). Browser recording stops around 58.5 seconds; formats include webm/ogg/mp4/m4a/wav (src/components/voz/useDictado.ts:9-11; src/lib/voz/limites.ts:3-6).

VPS, observed live on 2026-10-25: docker ps showed voz-decoracion Up 2 weeks (healthy), image voz-decoracion/voz:fw1.2.1-small-1; demo-decoracion Up 6 hours (healthy). GET http://127.0.0.1:8000/salud inside the voice container returned 200 {ok:true, modelo:small, cargado:true}. A GET from the demo-decoracion app container to its configured VOZ_URL + /salud also returned 200. The app’s inspected environment had VOZ_ENABLED=true and VOZ_URL pointing to internal http://voz-decoracion:8000. The active release is /opt/deployments/pictures/releases/112ebdc6fcdbab8111b7893dd4501891e35da18a; its compose declares env_file /etc/demo-decoracion/demo.env. The voice compose is /opt/voz-decoracion/compose.yaml, with secret env_file /etc/voz-decoracion/voz.env (the redacted env read showed only VOZ_SECRETO), service attached to internal stack_web with no host port. Model/runtime: remote code pins faster-whisper 1.2.1 and Systran/faster-whisper-small at a specific model revision in /opt/voz-decoracion/Dockerfile; live env reports model name small and the faster_whisper/ctranslate2 modules are installed. Limits/config in compose: 60 s (+1 s decode grace), 2 MiB, 30 s service timeout, 2 concurrent jobs + 4 queued, 4 CPUs and 2 GiB memory (advin:/opt/voz-decoracion/app/main.py:23-34, 111-137; compose.yaml:13-37).

Latency evidence: no audio fixture is present in this checkout, so no new transcription POST was sent. Existing VPS logs (tail) contain same-day entries for a 3.04 s sample with 97,332 bytes: 4,151 ms and 3,271 ms total (computes 4,127 ms and 3,270 ms, queue wait 23 ms and 0). This is existing-log evidence, not a controlled benchmark. Historical logs also show a full-queue 503 and repeated 401s for timestamp/signature issues; the bounded retry/anti-replay logic makes clock skew and burst traffic relevant risks.

Origins: this worktree’s .env.local has VOZ_ENABLED false or missing. The deployed VPS app container is true. Unauthenticated GETs to /api/voz/transcribir on both https://demo-decoracion.vercel.app and https://185-147-157-25.sslip.io returned 401, by the route’s auth contract; the public response intentionally does not disclose enabled state. Vercel environment values were not available in this task, so Vercel VOZ_ENABLED and its VOZ_URL remain UNVERIFIED. For Vercel to reach the VPS-only speech service, its VOZ_URL must be externally routable and share the HMAC secret, but that deployment setting was not observed.

## Findings, risks, and recommendations for brief design

Findings: Happia has a live bookable service and package catalogue, but no observed venues/themes/carts; the advisor currently uses package data, not service images or venue inventory. Photo originals and feedback persist, but only free-form prose is the first look. Budget and organiser priority are already structured; brief versions exist, while current output shows only the latest. Voice is healthy and enabled in the VPS app, but Vercel enablement is unknown.

Risks: event/theme package fit is unknowable from current fields; displayed estimates omit configurable quantities and assume COP; model-generated photo feedback can be saved without deterministic customer-turn validation; raw history exists as versions but not as a brief-facing change timeline; Vercel voice reachability/configuration is unverified. Short voice requests take roughly 3–4 seconds in the observed logs, with a documented queue-full incident.

Recommendations: expose brief version history as dated field-level changes; preserve budget/currency and organiserPriority already supported; add per-photo customer-confirmed keep/avoid points and link them to attachment IDs; persist a validated first-look object with style, colors, visible elements and confidence, clearly distinguishing model inference from customer confirmation. Reuse reference-analyze color/element capabilities selectively, with an advisor-specific schema rather than coupling the brief to balloon geometry. Treat Happia venue/theme support and package estimate assumptions as explicit gaps until upstream data or confirmation exists.
