# REQ-007 parity report: balloon counts and price, Python vs globos3d, on the 28 catalogue ideas

## 1. The contradiction, resolved

**Both reports used the same Python count.** For all 28 ideas these four numbers are identical, idea by idea:
`planes-ideas.json → globos` (Phase 1, via `casos-motor-guiada.ts`), `plan_resuelto.totales.total_unidades` (Phase 2,
`comparar-precios-ideas.ts`), the sum of the stored plan's structure `lineas`, and the sum of its `compras`
(`unidades_necesarias`). `material_estimate.balloons` is the same as well. Total: **2,403**. Only two ideas carry an
`armado_*` (06 and 08, both `armado_columna`). For those, the armado's own count (11 layers × 4 R-12, plus 1 R-36 in 08)
is also exactly the stored count, so plan.py used it. This report did not re-run `/plan/resolve`, because the stored
plan already *is* the resolve output on this snapshot (Phase 2's oracle matched 38 plans).

So the two reports differ on **interpretation**, not on the Python input:

| Claim | Verdict |
|---|---|
| Phase 1: engine counts ×1.38 overall, ×1.48 on complete ideas; organic pieces count much more because of R-5 fill | **True.** Re-measured on engine 1.1.0: 3,384 vs 2,403 (×1.41); ×1.51 on the 26 built ideas. Phase 1's 3,327 came from engine 1.0.0, before the colour fix in 588d2afd. One correction: Python's organic mix is R-12-dominant (24% R-5 / 68% R-12 / 5% R-18), not "18-inch". |
| Phase 2: engine ≈ 0.66× Python's price, "almost all of it is counting", "engine counts fewer in ideas with `armado_*`" | **The ratio is right; the attribution is wrong.** About 38 of the 34–35 points of discount come from **packaging**: Python's stored plans may only buy the allowlisted variants, which are almost all 50-packs. Counting adds back about **+3 to +5 points**, so the engine's materials cost slightly *more*. "Fewer in ideas with `armado_*`" applies to one idea only (08: 40 vs 44 R-12 per column). Fewer balloons also holds for the three classic arches, which have no armado. |

How the price falls while the count rises:

1. **Packaging (dominant).** The `allowlist` stored with each idea contains 172 "PAQUETE X 50" variants, 43 "X 6",
   6 "X 3", and only 7 smaller bags. Python therefore buys a full 50-pack for every colour × size, even when 3 balloons
   are needed (idea 05: 19 packs for 102 balloons). Python's stored purchase cost is **3.25× its consumption cost**
   ($2,999,155 vs $921,536 over the 28 ideas). The engine's `python` policy picks the cheapest combination of all
   presentations (12/20/50).
2. **Size mix.** Most of the engine's extra balloons are R-5 at about 123–152 COP each. Python's are R-12 at 261–330 and
   R-18 at 1,037–1,200. Count goes up by 41%, but material value goes up by only 16%.

and 25 the stored Python lines use variants that aren't in the crosswalk: crema, multicolor):

## 3. Per-structure explanation and verdict

Evidence used:

- **Official formulas.** `SEGUIMIENTO.md:94-101` gives R-12 at 25 cm = 5 quartets/m (R-9: 7, R-5: 10), a vertical pitch
  of 0.8 d, and the column layer count = height / (0.8 d) (`services/ai-api/app/columna/medidas.py:27`).
- **Industry research** (`investigacion-guirnalda.md:228-230`, sources cursodeglobosonline, BalloonBuilder). Organic
  garland density is light 13–20 / standard 20–26 / full 26–40 balloons per metre. The mix is about 30% 5", 60% 11",
  10% 16" (Mix A), or 25–35% 5" / 40–50% 12" / 15–20% 18" / 2–5% 24" (Mix B).
- **The reference photo of each idea.** `pistas_conteo` / `conteos_referencia.globos_foto` is a vision estimate of the
  real build (confidence 0.88–0.95). It is an independent yardstick, but not ground truth. Python's stored counts were
  partly *adjusted toward* it (`decision: ajustado`), so their agreement with it is partly by construction.

### Classic arch (01, 02, 14): 145 / 153 vs 112 / 120

- **Python:** classic mix (100% R-12) and λ_lujosa 4.5 give **26.6 balloons/m = 6.6 quartets/m**. With `media` it would
  be 21.3/m, and with `sencilla` 16.5/m.
- **Engine:** pitch 0.8 × 25 cm = 20 cm, which gives **5 quartets/m** (`trenza.ts`, `PASO_POR_DIAMETRO`). `densidad` is
  ignored on quartet pieces, and the engine warns about it (`espec-a-escena.ts:71`).
- **Verdict: the engine is right for the stated metres.** It matches the official 5 quartets/m exactly. 6.6 quartets/m
  of 25 cm balloons would need a 15 cm pitch, which is below 0.8 d. That's only possible with R-12 under-inflated to
  about 19 cm.
- The photos read 38 and 45 quartets (152 / 180), which is closer to Python. The most likely reason is that the photo
  arches are bigger than the 2.4 × 2.2 the analysis estimated. Python absorbed that by being "lujosa". This doesn't
  resolve at the plan level.
- **Owner question:** do you inflate R-12 to 25 cm in classic arches? If so, the engine's count is the one to quote for a
  customer who says "2.4 × 2.2".

### Classic column (08 ×2, 29 ×2; 06)

- **08:** Python 44 R-12 + 1 R-36 per column, straight from `armado_columna` (11 layers drawn from the photo: "11 capas
  en espiral"). The engine builds 40 + 1, because it uses `ceil(200/20)` = 10 layers and **ignores the armado's explicit
  layer list**. **Python is right** (−9% in the engine).
- **29** (two 0.7 m bases): 15 vs 16 per column. **Parity.**
- **06** (11 single-colour rings in 6 colours): the engine hits `MAX_COLORES_TRENZA` and falls back to the **organic
  twin**, which gives 75 balloons (44 R-5, 16 R-9, 11 R-12, 4 R-18) instead of 44 R-12. **Python is right.** This is a
  wrong representation, not a counting nuance. The idea goes to Python anyway, because R-18 Azul Caribe isn't sold.

### Organic semiarc (03, 04, 05, 10, 12, 13, 15, 17, 20, 31): Python 829, engine 1,334, photo 1,038 (9 pieces with a photo: 754 / 1,149 / 950)

- **Python:** 22.9/m, with 24% R-5, 68% R-12, 5% R-18.
- **Engine:** 36.8/m, with 56% R-5, 17% R-9, 20% R-12, 7.5% R-18.
- **Photo:** about 31% small, the rest medium to giant.
- By count, the photo sits between the two: Python −20%, engine +21% on the pieces with a photo. By surface, both
  undershoot the photo (photo 1,237 R-12-eq; Python 690; engine 727).
- Colour-by-size also differs (see §7). The engine places premium colours mostly in the R-5 filler:
  - Reflex Dorado Rosa, about 2.2× the price of a Fashion colour: 43 of 49 in 05, 42 of 46 in 17. Python spreads it
    across 21–24 R-12.
  - Cristal Rojo in 19: 16 of 16 are R-5.

  That is a large part of why 05, 17 and 19 quote at 0.45–0.47×. It also changes the look, because the accent colour
  shrinks to 12 cm balloons.
- **Verdict:** Python's **count and small-balloon share** are closer to the photo and to industry practice. The engine's
  **large-balloon share** (R-18 7.5% vs Python 5%) is closer to the photo and to Mix B. Neither is "right". The engine's
  excess is R-5 gap-fill, not extra metres.

### Organic garland (09, 11, 15b, 16, 18, 19, 22): Python 404, engine 793, photo 420 (6 with a photo: 345 / 699 / 355)

- Python sits at 21.4/m, which is "standard" (20–26/m). It is within 3% of the photos and has 26% small balloons
  (photo: 26%).
- The engine sits at **42/m**, above the industry "full" ceiling of 40/m, with 63% R-5.
- The engine's **density works backwards**. The same 2.4 m garland gives sencilla **112**, media 102, lujosa **94**
  (also 04: 208 / 172 / 152; 11: 268 / 223 / 203). `FACTOR_DENSIDAD` removes structure balloons, and the gap-filler
  (`organico.ts`, `RELLENO_TUPIDO`) then covers the holes with *more* R-5.
- The default envelope also drives the count. At `grosorM` 0.35 the same garland gives 62 balloons (Python 59). At 0.45
  (the default) it gives 94.
- **Verdict: Python is closer to the real build.** The engine over-counts by about 2× through filler; its surface is
  only +8%.

### Organic column (07 ×2, 12b, 30): Python 170, engine 311, photo 100 for 07 (Python 87 / engine 140)

- Same mechanism as the garland: 30 gives 60 vs 133, 81 of which are R-5.
- **Verdict: Python is closer.**

### Aro (28 built; 27 is partial → Python)

- 94 vs 219 (116 R-5, 82 R-9, 21 R-12). The engine count includes 2 balloon flowers (7 each). The photo gives 85.
- The engine's R-12 share is just 10%.
- **Verdict: Python is closer.** The engine's aro is almost all filler.

### Garland "clasica" (24, 25)

- **24** (single colour, called "Guirnalda orgánica" in the plan): the engine builds a **R-9** quartet trenza
  (`FORMATO_GUIRNALDA = "R-9"`, `constructores-clasicos.ts:29`). That gives 72 R-9 at 7 quartets/m, which is consistent
  with the official R-9 figure. But the plan's `clasica` mix is R-12, and Python gives 51 R-12. The engine ignores the
  mix.
- **25** (3 colours) falls back to the organic twin: 94 balloons, R-5 heavy, vs 64 R-12 (photo 75).
- **Verdict:** Python follows the plan. The engine's behaviour depends on the colour count rather than on the plan.

### Bouquet (03, 16 ×2): 6 / 12 / 10 on both sides. Parity.

### Not built by the engine

- 03 `centro_mesa` (5 balloons) has no constructor.
- 27 partial aro (151) isn't supported.
- Both take the Python path, as designed.

What this means for quotes:

- **Switching to the engine lowers library-idea quotes by about 35% (`python` policy) or 31% (`mas_barato`).** About 38
  points of that would happen **even with Python's exact counts**, because it comes from dropping the 50-pack allowlist.
  That is a pricing decision (P-035 plus "should library ideas keep the 50-pack-only allowlist?"), not an engine
  property.
- **Counting by itself:**
  - Organic pieces get about **10–22% more expensive**, because of the R-5/R-9 filler and extra colour×size lines that
    each need a pack.
  - Classic arches get **24% cheaper**: 5 vs 6.6 quartets/m.
  - The aro gets cheaper in packs, even though it holds more material.
- `python` vs `mas_barato` matters most on classic arches ($105,963 vs $142,668). The single plan-wide 8% reserve fits in
  the leftover of packs already bought, while per-line merma forces bigger packs.
- Per idea (stored → Python counts with `python` / `mas_barato` → engine `python` / `mas_barato`), see the table in §6.

## 5. Recommended engine fixes (before the switch, ranked by quote impact)

1. **Organic gap-fill cap (garland, semiarc, column, aro).** Keep R-5 at about 25–30% of the count, which is what the
   photos (26–31%), Python (24–26%) and the industry (25–35%) agree on. Fill the envelope with structure balloons
   (R-12/R-18) instead. A cheaper alternative is to calibrate the default `grosorM`: a 0.35 m garland gives 62 vs Python
   59. Accept when organic counts land within about ±20% of Python per metre and the R-5 share is ≤ 35%. In the same
   fix, spread each colour's weight across sizes, so premium colours (Reflex, Cristal) aren't concentrated in R-5
   filler (05, 17, 19).
2. **Make `densidad` monotonic.** Today sencilla gives *more* balloons than lujosa. Density should change coverage (allow
   holes or a thinner tube), not swap structure balloons for filler. Add a golden: count(sencilla) < count(media) <
   count(lujosa) for every organic structure. This is an orphan-property defect: `FACTOR_DENSIDAD` is consumed and then
   cancelled out by the filler.
3. **Honour `armado_columna` (and later the other `armado_*`).** When a structure carries an explicit layer list, build
   exactly those layers (08: 11 × 4). Single-colour rings must not trigger the 4-colour trenza limit (06: it should stay
   44 R-12 in rings, not become organic).
4. **Classic garland size.** Use the plan's mix (`clasica` = R-12) instead of the hard-coded R-9. When colours don't fit
   the trenza, prefer the Python path (or colour bands) over the organic twin, which changes the count and the size mix
   (25).
5. **Classic arch: no code change; owner decision.** The engine follows the official 5 quartets/m. If the owner wants
   "lujosa" classic arches to mean tighter clusters (smaller inflation), map density to inflation explicitly. Don't copy
   Python's λ, which isn't physical for quartets.
6. **Pricing (not engine):** the owner should decide P-035 and whether library ideas keep the 50-pack allowlist. That
   decision moves quotes more than all the counting fixes combined.

## 8. Reproduce

```
cd C:/Users/davidt/Downloads/e6c
NODE_OPTIONS=--use-system-ca npx tsx --conditions=react-server scripts/motor/paridad-ideas.ts <out.json>
```

The JSON holds, per idea, the Python view (per structure: medidas, densidad, mezcla, `eje_m`, lines by size and colour,
armado count; `compras`; `material_estimate`), the engine view (per piece: spec measures, BOM by format and colour, box)
and the price decomposition. Density and thickness sweeps were run ad hoc with `armarDesdeEspec` on idea specs with
`densidad` / `medidas.grosorM` / `medidas.largoM` overridden (numbers in §3).

Caveats:

- Photo counts are vision estimates, and Python's stored counts were partly adjusted toward them.
- "Material value" uses the cheapest unit price per balloon.
- The Python column is the stored resolve on snapshot 13a9…; a live `/plan/resolve` on a newer snapshot could differ
  in mix where the catalogue changed.
