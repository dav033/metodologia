## Cross-cutting evidence and constraints

- AppShell bypasses the CRM shell for `/login`, `/about`, `/privacy-policy`, and `/p/*`; middleware lets public note links through without an account. Keep the new authenticated palette outside those routes.
- Public note tokens are capabilities in the URL; `/p/[token]/layout.tsx` sets `no-referrer`. Preserve this security behavior.
- Tasks and notes currently have separate Ctrl/⌘K palettes, scoped to their layouts. A unified palette should reuse the existing task and note searches and remove duplicate hotkey listeners.
- Permission checks exist in route wrappers and controls; menu filtering is not a substitute for backend authorization.
- Invoice upload validates file type and size, reports progress/errors, and calls an upload-and-scan path. Do not replace it with a purely visual drop interaction.
- The task calendar drag/drop reschedules date and assignee, while the board uses `@dnd-kit` with keyboard support. Any replacement must preserve the mutation, data semantics, keyboard path and announcements.
- Note editor is TipTap with task/table/image/mention-style extensions; do not replace its schema or editor engine with a gallery block.
- QBO reports and project financials are accounting data, not decorative UI. Preserve source ownership, money values, date intervals and prefetch behavior.
- Block names above come from Bencho's official gallery list (`https://bencho.dev/`). The exact implementation, dependency list and accessibility behavior of a block must be checked from its copied source before adoption. Bencho's copied blocks are MIT; preserve the copyright notice for substantial source copies and do not copy site branding or licensed photos (`https://bencho.dev/licence`).

## Full catalog disposition

The official source registry exposes 63 entries. The audit compared the full registry with all 59 frontend routes and the authenticated shared shell. These are source blocks, not a production-ready component package. The selected and implemented blocks are `checklist` (task subtasks), `tag-input` (task labels and selected note labels), and `image-compare` (local restoration photos).

Existing Maros controls remain the better fit for these blocks: `magnet-select` (Radix selects/filters preserve native keyboard behavior), `seek` (the global `cmdk` search is functional and touch-keyboard compatible), `swipe-row` (task cards already expose actions and keyboard access; swipe-only actions would hide them), `upload-dropzone` (invoice drop/camera/file picker already validates type/size and handles progress/errors), `time-scrubber` (calendar and finance inputs need exact dates), `liq-arrange` (workspace and note trees already support pointer plus keyboard reorder), `browser-tabs` (detail tabs are URL-backed and are not user-reorderable), `slide-confirm`, `hold-delete`, and `confirm` (existing dialogs preserve deliberate, accessible confirmation), `picker` (existing selectors keep domain-specific filtering and validation), `label-input` (the task/note label flows now show persisted selected chips without replacing their data contracts), and `toasts` (Maros already uses Sonner for actionable feedback).

These blocks would need a product workflow or persistence contract Maros does not currently expose: `voice-note` (no audio-note API or stored media contract), `emoji-reactions` and `like` (no reaction entity or persistence contract), and `one-time-code` (authentication does not use OTP). `roster` is a fake demo user list and cannot replace server-backed assignment.

No route has a clear CRM use for these visual, game, hardware, or self-contained demo blocks; they remain out: `asset-swap`, `ascii-wake`, `carousel`, `palette` (design-palette generator, not command search or fixed label colors), `aspect`, `tilt`, `sound`, `drag-ball`, `humidity`, `glass-bubble`, `rolling-counter`, `dynamic-island`, `foggy-glass`, `scratch-card`, `heat-word`, `mb-spot`, `mb-holo`, `mb-deck`, `mb-compare`, `signature` (no signing workflow), `eye-tracker`, `card-stack`, `image-accordion`, `todo-tower`, `particles`, `generate`, `step-player`, `stepper` (no multi-step workflow warrants replacing the existing forms), `fold`, `action-node`, `pull`, `escape`, `slosh`, `liq-create`, `liq-toggle`, `toolbar`, `radial`, `sleep`, `icon-bar`, `dock`, `progress`, and `command` (chat demo with no-op handlers). The `command` block is a chat composer, not an app navigation palette.

The adopted and retained-control entries above are documented once by their disposition. No remaining catalog entry has a clear fit that would improve a real CRM flow while preserving Maros' current behavior. This is a scoped fit decision, not a claim that every route needs a new control.
