00600 |    <para>
00601 |     Creating an index can interfere with regular operation of a database.
00602 |     Normally <productname>PostgreSQL</productname> locks the table to be indexed against
00603 |     writes and performs the entire index build with a single scan of the
00604 |     table. Other transactions can still read the table, but if they try to
00605 |     insert, update, or delete rows in the table they will block until the
00606 |     index build is finished. This could have a severe effect if the system is
00607 |     a live production database.  Very large tables can take many hours to be
00608 |     indexed, and even for smaller tables, an index build can lock out writers
00609 |     for periods that are unacceptably long for a production system.
00610 |    </para>
00611 | 
00612 |    <para>
00613 |     <productname>PostgreSQL</productname> supports building indexes without locking
00614 |     out writes.  This method is invoked by specifying the
00615 |     <literal>CONCURRENTLY</literal> option of <command>CREATE INDEX</command>.
00616 |     When this option is used,
00617 |     <productname>PostgreSQL</productname> must perform two scans of the table, and in
00618 |     addition it must wait for all existing transactions that could potentially
00619 |     modify or use the index to terminate.  Thus
00620 |     this method requires more total work than a standard index build and takes
00621 |     significantly longer to complete.  However, since it allows normal
00622 |     operations to continue while the index is built, this method is useful for
00623 |     adding new indexes in a production environment.  Of course, the extra CPU
00624 |     and I/O load imposed by the index creation might slow other operations.
00625 |    </para>
00626 | 
00627 |    <para>
00628 |     In a concurrent index build, the index is actually entered as an
00629 |     <quote>invalid</quote> index into
00630 |     the system catalogs in one transaction, then two table scans occur in
00631 |     two more transactions.  Before each table scan, the index build must
00632 |     wait for existing transactions that have modified the table to terminate.
00633 |     After the second scan, the index build must wait for any transactions
00634 |     that have a snapshot (see <xref linkend="mvcc"/>) predating the second
00635 |     scan to terminate, including transactions used by any phase of concurrent
00636 |     index builds on other tables, if the indexes involved are partial or have
00637 |     columns that are not simple column references.
00638 |     Then finally the index can be marked <quote>valid</quote> and ready for use,
00639 |     and the <command>CREATE INDEX</command> command terminates.
00640 |     Even then, however, the index may not be immediately usable for queries:
00641 |     in the worst case, it cannot be used as long as transactions exist that
00642 |     predate the start of the index build.
00643 |    </para>
00644 | 
00645 |    <para>
00646 |     If a problem arises while scanning the table, such as a deadlock or a
00647 |     uniqueness violation in a unique index, the <command>CREATE INDEX</command>
00648 |     command will fail but leave behind an <quote>invalid</quote> index. This index
00649 |     will be ignored for querying purposes because it might be incomplete;
00650 |     however it will still consume update overhead. The <application>psql</application>
00651 |     <command>\d</command> command will report such an index as <literal>INVALID</literal>:
00652 | 
00653 | <programlisting>
00654 | postgres=# \d tab
00655 |        Table "public.tab"
00656 |  Column |  Type   | Collation | Nullable | Default
00657 | --------+---------+-----------+----------+---------
00658 |  col    | integer |           |          |
00659 | Indexes:
00660 |     "idx" btree (col) INVALID
00661 | </programlisting>
00662 | 
00663 |     The recommended recovery
00664 |     method in such cases is to drop the index and try again to perform
00665 |     <command>CREATE INDEX CONCURRENTLY</command>.  (Another possibility is
00666 |     to rebuild the index with <command>REINDEX INDEX CONCURRENTLY</command>).
00667 |    </para>
00668 | 
00669 |    <para>
00670 |     Another caveat when building a unique index concurrently is that the
00671 |     uniqueness constraint is already being enforced against other transactions
00672 |     when the second table scan begins.  This means that constraint violations
00673 |     could be reported in other queries prior to the index becoming available
00674 |     for use, or even in cases where the index build eventually fails.  Also,
00675 |     if a failure does occur in the second scan, the <quote>invalid</quote> index
00676 |     continues to enforce its uniqueness constraint afterwards.
00677 |    </para>
00678 | 
00679 |    <para>
00680 |     Concurrent builds of expression indexes and partial indexes are supported.
00681 |     Errors occurring in the evaluation of these expressions could cause
00682 |     behavior similar to that described above for unique constraint violations.
00683 |    </para>
00684 | 
00685 |    <para>
00686 |     Regular index builds permit other regular index builds on the
00687 |     same table to occur simultaneously, but only one concurrent index build
00688 |     can occur on a table at a time.  In either case, schema modification of the
00689 |     table is not allowed while the index is being built.  Another difference is
00690 |     that a regular <command>CREATE INDEX</command> command can be performed
00691 |     within a transaction block, but <command>CREATE INDEX CONCURRENTLY</command>
00692 |     cannot.
00693 |    </para>
00694 | 
00695 |    <para>
00696 |     Concurrent builds for indexes on partitioned tables are currently not
00697 |     supported.  However, you may concurrently build the index on each
00698 |     partition individually and then finally create the partitioned index
00699 |     non-concurrently in order to reduce the time where writes to the
00700 |     partitioned table will be locked out.  In this case, building the
00701 |     partitioned index is a metadata only operation.
00702 |    </para>
