## 2. Three genuinely different directions per UI subplan, the owner picks one
**Product rule:** for every UI subplan the Designer system produces **three directions** (default; `--directions N` to change) and the owner chooses one in the web UI. A direction is a complete design language, NOT a re-skin. Two directions must differ in structure, not only in colour: define the axes (at least: concept taken from the product's world, layout archetype/composition and navigation model, type pairing and scale, density and shape language, signature component treatments, colour logic, **motion language** (easing family, durations, choreography, what animates and when)). A palette/font/dark-mode swap on the same layout is a failed direction.
- **Freedom:** the Designer gets wide creative freedom: the kit's components are a base it may restyle, recompose or replace; it must commit to a point of view, name the direction, state its one memorable thing and why it is not the default (the slop tells listed by the sources above are refused unless the brief earns them). Pictures' world (SEMPERTEX balloon decoration, a 3D decoration planner for event decorators, Spanish-first, see the REQ-021 SPEC read-only) is the source of identity; the owner dislikes generic SaaS look (cream+terracotta, purple gradients, identical card grids, hero-metric tiles, eyebrow labels).
- **Mechanism (you design the details, these are the constraints):** `design draft REQ ref` (first draft, `--fresh`, feedback-triggered redo) launches N Designer delegations in parallel, one per direction, each with a different creative seed (seeds are stances, e.g. an operational/editorial-dense one, a kinetic/expressive one, a tactile/playful one derived from the product; not palettes) and each writing its own files, e.g. `design/<ref>@vN.dir-a.html` + a short direction note (name, concept, axis table, why not default). The behavioural contract (`<ref>@vN.md`: views, states, flows, criteria) stays ONE source of truth shared by the directions; the visual sections are finalised for the chosen direction after the pick (a finalise step by that direction's Designer). Handle failure of one direction without losing the others. Concurrency limits and quota: keep delegations bounded and make N configurable.
- **Distinctness gate:** add `kit/compare_directions.py` (or similar) that measures how different the directions' mockups really are (fonts used, layout/DOM structure skeleton, computed-style distributions, motion keyframes/easing sets) and FAILS when two directions are too similar; the Designers must run it and the system shows its result. Add the Designer-written axis table to the direction note and reject notes that claim differences the mockups don't have.
- **Web UI:** in the Plan tab design view and the review page: a direction switcher (A/B/C with names and live thumbnails), a side-by-side comparison, the axis table, full-screen preview per direction (existing mockup-nav/full-screen tooling must keep working per direction), a «Elegir esta dirección» action (owner only, recorded in the activity feed, tells the Planner via `notify_planner`), un-chosen directions kept in history, comments/feedback addressed to a direction (e.g. «layout de A con el movimiento de C»). A UI subplan cannot be confirmed/approved until a direction is chosen (add to the confirmation checks with a clear Spanish message, no fail-open). Update `Plan` docs (`references/requirements.md` §8, `agents/planner.md`, `agents/designer.md`).

## 3. Lots of animation (owner explicit; overrides `mockup-craft.md`'s «motion only answers a user action»)
Rewrite the motion rules: mockups are expected to be richly animated — page-load choreography, staggered reveals, view/state transitions, hover/press/focus micro-interactions, scroll-driven or parallax effects where the screen scrolls, animated typography and backgrounds (React Bits-style), shared-element transitions between views, skeleton shimmer, success/error confirmations, delightful empty states — each direction with its OWN motion language (different easing, timing and choreography, not the same fade-and-slide-up on everything). Constraints that stay: transform/opacity first (60 fps), the three motion profiles (subtle/natural/expressive; expressive default in mockups) wired to tokens, full `prefers-reduced-motion` degradation, animations never hide content or break AA contrast mid-animation, heavy effects pause off-screen/in hidden tabs, a settled/still mode (e.g. `?still=1` or reduced-motion) so `audit_mockup.py` measures the final state and so screenshots are stable; extend the audit to flag missing reduced-motion handling and layout shift. The libraries (Animate UI, React Bits, Motion/GSAP skills above) are the toolbox; the mockup builder must be able to inline Motion or GSAP when a direction uses them (self-contained, no network).
