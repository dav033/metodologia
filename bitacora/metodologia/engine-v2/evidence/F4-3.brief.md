## Requirements (TDD; fail-first where feasible)
1. `PLAN_SCHEMA_CAPABILITIES` adds `"1.3.0"`. The loader parses optional `subplans` and `composition_gates` and task
   `subplan_id`/`ui`/`kind` into immutable read-only structures (malformed shapes → `PLAN_INVALID`, never an exception).
   Fingerprints used by `rebase_run`/`apply_plan_revision` include `subplan_id` and `ui` for 1.3.0 tasks only (legacy
   fingerprints byte-identical; test with an existing fixture).
2. Task metadata handed to M2 (`AssignmentRequest`/`PlanRoutingRequest` classification metadata) and to M3 (`StartOrder`/task
   meta) gains, for 1.3.0 plans with subplans only, optional `subplan_id`, `review_axis: "visual"` for a subplan's
   `ui.visual_review_task`, and `ui` when declared. Legacy requests unchanged (golden comparison).
3. Derived view `subplan_status(plan, state)` → per subplan `open | auditing | accepted | published` (accepted = audit task
   completed; published = adapter fact recorded). Never stored as task state.
4. Audited fact operations (observations; they do not change task/attempt state): `record_subplan_version(subplan_id, version,
   commit, manifest_sha256)`, `record_composition(candidate|published|rejected, composition_id, members, manifest_sha256,
   reason?)`. Persisted in run state additively (run-state schema bump with in-memory upgrade like schema 1→2→3; older states load;
   an older M1 refuses the new schema rather than dropping it — follow the existing pattern).
5. Composition-gate readiness: a `composition_gates[].task` becomes dispatchable only when every member subplan has a recorded
   published version (the facts of req. 4); until then it stays `pending` with an attention reason `composition_waiting`.
   Legacy plans and plans without subplans: no change.
6. Adapter: pass 1.3.0 through; expose thin wrappers for the fact operations for later wiring (F4-9). No other methodology module
   changes.
7. README: contracts table, states, new audit kinds, errors.
