# Plan — REQ-017 — Scheduler M4 Agent Monitor

## Approach
Add an isolated, standard-library `bt_scheduler_monitor` that consumes a bounded, versioned M3 output stream and emits allowlisted normalized events. Keep M1 lifecycle events unchanged; add a separate audit-only incident reference port to M1 and a provenance-aware read-only metric source to M2. A local M4-owned SQLite store provides cursors, incidents, history, retention and an at-least-once outbox. Provider fixtures and simulators establish deterministic behavior before any optional live CLI smoke.

## Global constraints
- M1 remains the sole authority for task/attempt state; M2 chooses routes; M3 owns process lifetime and raw bounded output artifacts; M4 observes and stores normalized evidence; M5 owns recovery; M6 verifies results.
- Do not call model/provider APIs, read credentials, launch real agents, signal processes, deploy, or edit legacy `RUN.json` behavior.
- Keep raw provider bytes and arbitrary project text out of M4 persistence. Persist allowlisted fields, bounded redacted evidence or its digest/count/offset, and withhold excerpts if redaction fails.
- Keep stream reads independent of M4 persistence with bounded frames and queues; expose loss as a gap. Preserve current M1 lifecycle contracts while adding a separately versioned M3-to-M4 stream port.
- Keep all contracts versioned; unknown values remain explicit. Use UTC for audit time and monotonic time plus boot identity for elapsed thresholds.
- Use Python standard library only in `bt_scheduler_monitor`; one public API, one methodology adapter, no sibling `bt_*` imports, no service/database dependency, and no process-control API.
- Owner-approved retention and evidence limits: 90 days for normalized event detail, 365 days for resolved incident detail, 730 days for daily aggregates, 512 MiB for database plus WAL, 16 KiB per normalized event, 4 KiB per evidence excerpt, and a bounded 10,000-frame / 16 MiB queue. Linux FIFO frames are at most `PIPE_BUF` (4,096 bytes on the target Linux platform) with at most 3,840 payload bytes. Preserve open incidents; at storage pressure prune eligible details, compact aggregates, then expose a degraded state and explicit gaps without claiming complete history. Set CPU/RSS/throughput targets only after the reproducible three-simulated-agent baseline in T12.

## Rulings
- Keep M1 lifecycle submission separate from the M4 stream tap; M3 currently has a direct lifecycle sink that can delay its supervisor, so M4 must use a bounded handoff and must not add work to that path.
- Treat Gemini CLI as a fixture target only until M3 has an authorized `gemini` route; use Antigravity simulator fixtures while `agy` is unavailable locally.
- Keep the proposed SQLite file separate from M1/M3 stores and legacy `bt_events`; only the owning module writes its records.
- The owner approved D-033: 90/365/730-day retention, the 512 MiB database-plus-WAL cap, bounded evidence, and the pressure policy above. Never evict an open incident to satisfy the cap.
- The owner approved D-034's configurable initial detector thresholds: 90-second missed-heartbeat, five-minute informational silence, 20 repeated activities in five minutes, two-second post-cancel drain grace, and a 30-second disagreement reconciliation window. Validate them against deterministic fixtures; none changes task state or controls a process.
- T12 sets CPU/RSS/throughput and p95 latency budgets from measured baseline data rather than estimates.
