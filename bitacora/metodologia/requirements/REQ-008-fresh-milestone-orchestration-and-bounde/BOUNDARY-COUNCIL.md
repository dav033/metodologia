# REQ-008 — Context boundary design council

This is design-time evidence, not an implementation or passing test of runtime R6 recovery.

Three independent `gpt-6-luna` agents at `medium` effort received separate solution briefs with no inherited conversation. Each proposed an alternative, then received the other two proposals and returned a critique. No agent edited code. The coordinator made D-017 after examining the source and capability evidence.

| Agent | Proposal | Peer-critique conclusion |
|---|---|---|
| `boundary_proposal_a` | Fresh structured Claude decisions; deterministic existing supervisor executes admitted actions and reconstructs bounded milestone state. | Adopt now only with verified effective tools; explicit wait when no eligible coordinator. A static Codex catalog alone does not prove runtime isolation. |
| `boundary_proposal_b` | Pinned public Codex model catalog preserving slug/auth with data-producing tools disabled; effective-request/runtime tests before eligibility. | Viable candidate, but not proved now. A small bounded non-data-tool allowlist could be sufficient; every route needs pre-delivery bounds and aggregate budgets. |
| `boundary_proposal_c` | Native orchestrators using wrappers and isolated delegates, with rotation and durable receipts. | Posthoc monitoring cannot prove a cap. Without blocking every bypass, this remains cooperative. Prefer A now and require proof before B. |

## Coordinator ruling

Choose A as the immediate enforceable architecture while keeping backend eligibility capability-based. The implemented runtime must preserve model/provider routing for workers, approvals, dependency scheduling, task verification and the same-terminal relay lifecycle. It must not infer success from model agreement or output claims.

The decisive evidence is the real Claude effective inventory (`StructuredOutput` only, no data tools/MCP), supported local flags and the absence of a proven equivalent Codex boundary. This is an availability tradeoff, not an assertion that Codex cannot ever support the mode. Explicit waits are preferable to silently dropping the context guarantee. Unsupported backends can become eligible after an actual tested adapter proves the boundary.

## Remaining proof

M2 must implement action validation, bounded receipts, fresh provider/session identity, foreground terminal behavior and checkpoint rotation. M3 must implement the autonomous persisted three-proposal/critique/ruling recovery protocol. This design council closes none of those runtime acceptance criteria by itself.
