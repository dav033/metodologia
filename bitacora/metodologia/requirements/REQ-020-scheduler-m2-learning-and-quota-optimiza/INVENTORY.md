### Attribution and provenance

- Subscription polling stores account-level percentages and reset times, not task or attempt IDs. Multiple concurrent tasks, external provider usage, account aliases and a reset can all change a percentage between polls; no per-task quota delta can be inferred from the current cache.
- `bt_events.extract_usage()` records provider-reported token fields separately. Missing token fields stay `null`; token counts, quota percentages, subscription capacity and reported cost are different units and are never converted into one another.
- M2 currently receives only aggregate `quota_status`, one pressure percentage, `observed_at` and `valid_until`. Window identities and per-window status are discarded before `Candidate` construction.
- `propose()` reads current caches only. Polling/network refresh remains owned by the subscription supervisor; a source error, stale row, future observation, reset without a post-reset sample or missing required window must remain unknown in strict mode.

## T6–T23 implementation boundary

- The isolated M2 package now exposes `QuotaObservation` cache normalization with API/schema 1.2.0 and `DemandEstimate` with separate provider-token and quota-percentage-point units. Both helpers are pure and bounded; M2 still does not collect quota or refresh a provider.
- Delta attribution requires the same effective account/provider/model/window, overlapping reads, one active task, an unchanged reported reset and explicit absence of external usage. Parallel work, reset crossing, unknown reset or possible outside use returns `attribution_unknown`.
- Exact-context estimates expose empirical min/median/max, source, sample count and a maximum one-day TTL; this is not a calibrated prediction. The methodology adapter continues to consume its current cached quota/history inputs; an estimate is not treated as observed task usage or refreshed from a provider.
- `batch.py` assesses route windows across base and model-specific scopes, reuses one result for aliases with the same effective provider account, and excludes only routes with a required stale, unknown, exhausted or conflicting window. It does not reserve quota or alter M1 state.
- `performance_events.py` now normalizes bounded M1 attempt/M1-applied verdict and M2 decision projections without importing M1/M4/M6 or touching their state. It binds plan/revision/task/attempt to the decision ID and selected route encoded in the attempt's opaque executor reference.
- Only a matching `applied`/`duplicate` independent verdict with explicit M1 application time, complete matching identities and non-synthetic sources becomes a PASS/FAIL history event. Claims, cancellations, infrastructure failures, non-applied/stale results, PASS without required acceptance evidence and mismatches remain ineligible. A stale delivery can be followed by an applied retry with the same verdict ID; reducer output is arrival-order independent and conflicting applied duplicates become unknown.
- `history.py` aggregates only those correlated events against a separate bounded context map. It reports unique attempts, eligible samples, coverage, Wilson uncertainty and non-quality outcome counts across exact context, complexity class, task family and route. Five verified samples are required before a level can expose its Beta(2,2)-shrunk ranking feature; below that, selection falls through to the next level and finally the existing deterministic baseline. Infrastructure failures remain outside PASS/FAIL quality counts. This is descriptive history, not a calibrated forecast.
- `learning_snapshots.py` persists those aggregates beside decisions in the M2 SQLite ledger. Source fingerprints bind canonical hashes of normalized events and context identities plus route, target, policy, cutoff and aggregate; raw source/task identities are not stored. Snapshots are append-only, unique, checksum-verified, capped at 10,000 rows and 32 KiB each, and exact replay returns the original timestamp/payload. Writable schema-1 files migrate to schema 2 without rewriting decisions; read-only schema-1 resolution remains valid. D-044 records rollback expectations.
- `temporal.py` evaluates historical features at sorted UTC epoch cutoffs using only M1-applied events with valid `applied_at`. It partitions all routes before replay reduction and route selection, ignores timestamped stale/invalid/noop deliveries, separates future observed metrics from the past-only feature, and fingerprints only pre-cutoff reduced events and contexts. It reports untimed attempt counts and makes no future-probability or calibration claim.
- `policy.py` defines `m2-route-policy-v1` as a fixed lexicographic policy after the existing hard filter. It accepts quality only from a matching T10 `ContextualHistoryAssessment` with at least five correlated samples; it never reads the adapter's uncorrelated legacy `RouteHistory` as a quality floor. Risk thresholds are supported but unset pending an approved value. Cost comparison requires one shared scale across all routes, and an upcoming reset only wins when its window has the maximum pressure. T15's batch selector consumes this route-ranking function; the current single-task `DecisionEngine` still uses the deterministic router reference.
- Public `plan_ready_batch()` adds bounded pure READY-task selection over up to 128 requests and 4,096 candidate/account edges. It requires one plan/revision/hash/time/slot snapshot, preserves hard route filters and T14 route order, and uses capacitated matching to maximize feasible assignments up to `free_slots`. Tasks with fewer eligible accounts are considered first, then stable task ID. Routes sharing `account_ref` share capacity; known active work is deducted from the declared account limit. A missing limit does not create an assumed per-account cap. The output includes policy rank, stable assignment/no-assignment reasons, route exclusions and canonical batch/input hashes, but no reservation. The existing M1 adapter's per-task loop remains unchanged until T18.
- T16 adds `batch_ledger.py`, exposed as `DecisionLedger.batch_decisions`, with append-only, content-addressed batch plans. It stores selected assignments/reasons, route exclusions and stable unassignment evidence without task prose, raw route-policy evidence or provider output. Plans are checksum-verified and bounded to 10,000 rows of 2 MiB each; exact replay returns the first payload, changed inputs create a new row, and updates/deletes/pruning are rejected. Writable schema-1 ledgers migrate through schema 2 to schema 3; writable schema-2 ledgers add only `batch_decisions`. Read-only schema-1 decision access and schema-2 decision/snapshot access remain supported. D-047 records compatibility and rollback.
- T17 adds `shadow.py` and the opt-in `compare_shadow_batch()` API. It compares deterministic READY-order routing against T15 capacitated matching using the same normalized snapshot, policy and explicit account concurrency; stable task differences and snapshot/comparison hashes make runs replayable. Disabled mode returns before reading inputs. The immutable comparison remains in memory and writes no ledger, reservation, dispatch or task state; no provider is called, schema 3 is unchanged, and M1 remains final authority. D-048 records this boundary and rollback.
- `executor_lookup.py` now owns read-only route/binding resolution; `ledger_errors.py` owns stable shared local-persistence errors, keeping `recorder.py` below 500 lines without changing its public lookup behavior.
- Existing `_history_snapshot()` still reads coarse legacy `bt_events` rows; those rows remain ineligible as correlated learning labels. T20 exposes exact-matched M4 `MetricSample` measurements through the optional monitor runtime, but does not turn them into correlated quality outcomes or require M4 at M1/M2 import time. Unknown quota values remain `None`.
- T21's fake-backed E2E exercises the shared M1/M2/M3/M4 and M1/M5 wiring. M1 continues to validate each M2 route/hash/quota proposal, own reservations and authorize retries; M5 wait/block decisions do not trigger a route loop.
- `test_scheduler_decision_adversarial.py` adds deterministic negative cases for stale, missing, reset, exhausted, aliased, externally used and retry evidence; unknown or unconfirmed facts fail closed.
- `bt_scheduler_decision_benchmark.py` compares FIFO, eligible round-robin, a frozen legacy router output, deterministic M2 and contextual M2 on one hashed 100-case/500-candidate fixture. Oracle accuracy/regret labels and quota-window coverage are synthetic fixture measurements only. The run has zero observed real quota-window and consumption-attribution coverage, zero real time-to-verified/human-intervention coverage, and no correlated route history for contextual ranking; it therefore falls back deterministically. Cross-case concurrency and provider cost are not measured.
