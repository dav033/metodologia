## Apply techniques conditionally

| Condition | Use |
|---|---|
| Contract defines navigation, labels, empty states, errors or confirmations | Specify consistent product terms, clear action labels and recovery guidance; route unresolved voice or behavior decisions as questions. |
| Contract defines hierarchy, layout or breakpoints | Specify content order and grouping, then describe how structure changes where content no longer fits. Include translation growth, zoom, RTL and overflow when the project supports them. |
| Contract defines design tokens or themes | Reuse project tokens. State the semantic role, supported themes and usage of each relevant token; separate raw values from roles. |
| Contract defines interaction or accessibility | Specify keyboard operation, focus, names, announcements and applicable WCAG 2.2 AA targets. Mark targets that need rendered checks. |
| Contract or enabled preview must cover multiple UI states | List applicable reachable states, use mock data and a state switcher in the optional preview, and ensure each criterion names its state. The contract remains source of truth. |
| Brief leaves aesthetic direction open and the contract needs a visual direction | **Only then** consult the `frontend-design` adaptation: derive a distinctive, coherent visual direction from confirmed product subject, audience and purpose. Record it as a proposal when the brief does not decide it. Do not generate or edit product code. |

The public sources do not define this project's approval gate, immutable contract versions, PLAN.json consumer impact or `design/` ownership. Those rules are defined by the private Designer skills and the runtime contract.
