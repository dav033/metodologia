# Functional subplan decomposition — Planner private skill

## Trigger and authority
Load after validating the overarching requirement and inspecting the repository, after drafting the general plan and **before** decomposing it into execution tasks. This skill specifies planned outcomes only. Planner never changes product code, approves plans, launches workers, chooses models/accounts or mutates scheduler state.

## Procedure
1. **Preserve the general plan first.** Derive objective, scope, exclusions, requirement IDs, actors, current architecture, external inputs, risks and acceptance; do not replace the main plan with a loose list of subplans.
2. **Choose functional seams.** Each candidate subplan represents an externally observable behavior of roughly medium user-story scale, not an arbitrary directory, technical layer or large epic. State inputs, outputs, invariants, negative cases and independently observable acceptance.
3. **Map owners and contracts.** Identify producer and consumer for every public API, schema, event, UI contract and shared resource. Distinguish dependency on a frozen **contract** from dependency on a completed **implementation**. A consumer can work against a validated contract, but must not treat unaudited implementation as accepted.
4. **Build subplan graph.** Assign stable IDs, requirement coverage, interface versions and bounded dependencies. Detect cycles and mutually-owned files; propose scope/contract correction when a purportedly independent subplan cannot stand alone.
5. **Plan verification borders.** Every subplan gets task-level checks, a real-entrypoint integration test, independent audit, findings ledger and acceptance identity. For risky/large subplans add internal checkpoints early; do not defer all adversarial review to the final milestone.
6. **Plan composition.** Define what will be tested with real producer/consumer implementations together, what can be reused by evidence and which conditions trigger reverify, reintegrate, change contract, rework or actual reimplementation.
7. **Recognize UI.** For every subplan with UI work, declare `ui {contract, version, design_task, visual_review_task}`. The `design` task precedes every `ui: true` task; Reviewer axis `visual` precedes the subplan audit. Plan responsive/state/flow coverage. The versioned contract path `design/contracts/<contract>@v<version>.md` is a project-repo convention, not a schema field constraint. Preview is a project setting and optional; the contract is mandatory. Planner plans this gate but never designs or approves the interface.
8. **Classify external checks.** Inventory needed environments and secret **names/locations only**, distinguish sandbox, authorized external, production and human-attested evidence, and plan a recoverable blocked result when permission/environment is missing.
9. **Challenge completeness.** Use existing WBS and adversarial-plan-review skills: trace every requirement → subplan → task → acceptance → evidence; identify orphan work and unresolved conflicts. Keep planned tests planned, not passing.

## PLAN.json 1.3.0 contract compatibility
Use the `SCHEMA-1.3.0.md` design record in the engine-v2 contract materials (outside the target project repo) as the field and validator contract. `subplans`, `composition_gates`, task `subplan_id`/`ui`, `kind: design`, and verification `environment`/`requires`/`authorization_needed` are native 1.3.0 fields. Never write them into a document with `schema_version` below 1.3.0. Legacy 1.0.0–1.2.0 plans remain valid and unchanged. Until engine consumers support 1.3.0, the adapter refuses publication with `PLAN_SCHEMA_UNSUPPORTED_BY_ENGINE`; report this and do not encode the data in unsupported fields or an auxiliary manifest as a workaround.

Subplans are optional in 1.3.0. A simple change may keep the no-subplans path. When present, each subplan belongs to one existing milestone and its member tasks share that milestone. Each requirement must belong to a subplan or be owned by a composition gate. Each subplan's `acceptance_criteria` must be exact text copied from acceptance criteria of its own tasks. Each `covers` item is a top-level requirement; tasks' `covers` stay within their subplan's coverage.

### Validator rules and corrections

| Rule / error code | Required plan shape | Fix when violated |
|---|---|---|
| `SUBPLAN_EDGE` | A task's cross-subplan `after` names only the producer's `defined_by`, `audit_task`, or composition-gate task, and the consumer subplan declares a matching `consumes` relationship. | Remove the hidden implementation-task edge; declare the correct consumed contract and edge to its allowed task, or merge coupled subplans into one coherent unit. |
| `LATE_CHECKPOINT` / `SUBPLAN_LATE_CHECKPOINT` | No dependency chain has more than six `implement`, `docs`, `design`, or `research` tasks between `test`/`audit` barriers. Within a subplan, only its own barriers count. A subplan with more than eight tasks has a `checkpoints` entry. | Add the earliest meaningful test/audit barrier at the first likely defect boundary; make it observe the behavior and add dependency edges so later work follows it. Do not defer discovery to a terminal audit. |
| `SUBPLAN_ORDER` — `implementation` | Every non-exempt consumer task follows the producer's `audit_task`; research/docs and the consumer's own `produced[].defined_by` tasks are exempt. | Order implementation consumption after the producer audit, or change the declared dependency to contract if a frozen contract truly suffices. |
| `SUBPLAN_ORDER` — `publication` | Every non-exempt consumer task follows a composition gate that includes the producer and excludes the consumer. | Add/order a producer publication gate first; keep the consumer's later integration gate separate and listing both subplans. |
| `COMPOSITION_MISSING` | Every cross-subplan `consumes` relationship has at least one composition gate listing producer and consumer; gate task is an integration test over accepted subplan audits. | Add a real-entrypoint composition test and gate listing both subplans, with criteria copied exactly from the gate task. |
| `UI_WORK_UNDECLARED` | Every 1.3.0 task whose expected path ends in a UI extension explicitly declares `ui` (true for UI work, false for a deliberate non-UI case such as a route handler). | Add `ui: true` and the Designer gate for actual UI, or explicit `ui: false` with a justified non-UI classification. |
| `UI_GATE_MISSING`, `UI_GATE_ORDER`, `UI_REVIEW_ORDER` | UI task belongs to a subplan with the required `ui` block; design is an ancestor of every `ui: true` task; visual review follows all UI tasks and is an ancestor of subplan audit. | Add the Designer `design` task and contract metadata, correct `after` edges, then put the Reviewer visual-axis audit before the subplan audit. |
| `FILE_EXISTENCE_CHECK` | Functional, integration and product command checks exercise behavior; existence/well-formedness probes alone do not qualify. | Replace `test -s`, `ls`, `stat`, `json.tool`, `jq empty`, `grep -q`, and similar probes with an observable behavioral check. They may remain for docs-only deliverables. |
| `EXTERNAL_ONLY_IMPLEMENT` | Each `implement` task has at least one command verification in `sandbox`; external checks belong to `test` tasks with a recoverable blocked result. | Keep implementation acceptance locally provable; move the external smoke to a `test` task and state its blocked/retry conditions. |
| `SECRET_VALUE_IN_PLAN` | `requires` contains resource names only (environment-variable names or `service:<slug>`); never values, credentials or credential-bearing URLs. Production checks state the owner's grant in `authorization_needed`. | Replace values with names and locations; describe the needed owner authorization without including a secret. |

Additional contract rules: every subplan has a `kind: test` integration task that exercises real entrypoints and a `kind: audit` task with every other subplan task as an ancestor; the audit includes that integration test in its ancestry. `checkpoints[].task` names a subplan `test` or `audit`. `produces[].defined_by` names a task that freezes the contract. A `consumes` contract names its producer and dependency kind (`contract`, `implementation`, `publication`); avoid implementation/publication cycles. Cross-cutting requirements belong to an explicit composition gate. A `human_attestation` verification uses `type: manual` and `expected`; every production verification has `authorization_needed`.

## Output
Return the subplan table plus the corresponding PLAN.json 1.3.0 fields: top-level `subplans` and `composition_gates`; task `subplan_id` and explicit `ui` where needed; `kind: design`; and verification `environment`, `requires`, and `authorization_needed` where applicable. The table covers ID, bounded objective, requirements, produced/consumed contracts, dependent IDs, internal task owners, testing/checkpoints, audit/integration tasks, composition gates, version gate and UI dependency. State adapter compatibility (`PLAN_SCHEMA_UNSUPPORTED_BY_ENGINE`) when relevant. Do not add non-schema sidecar fields. Mark planned tests as planned, not passing.
