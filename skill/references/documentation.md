# Bitácora (documentation)

The bitácora is the project's memory across sessions. Write it for a future reader who has none of today's
context — often that reader is you, next session. The script handles structure, dates and IDs; you write content.

```
~/bitacora/<project>/
  SUMMARY.md       what it is + current state           → REWRITE when state changes (≤60 lines)
  ARCHITECTURE.md  how it's built / how the process runs → EDIT IN PLACE when structure changes
  DECISIONS.md     decision log (D-001…)                 → APPEND ONLY
  PENDING.md       backlog (P-001…) by urgency × complexity → ADD lines; the script keeps it sorted
  TOOLS.md         servers, hosting, CLIs, storage access → EDIT IN PLACE (no secrets; see tools.md)
  INDEX.md         navigation map of the project          → GENERATED by the script, never edit
  project.json     workspace: repos by role (+ optional root) → `bitacora.py workspace add|remove|show|root`
  requirements/REQ-001-<slug>/SPEC.md, PLAN.md, HANDOFF.md, rounds/round-NN.json
  artifacts/                  HTML pages, diagrams, reports, mockups you create for this project
  2026-10/MONTH.md            month summary
  2026-10/W2/WEEK.md          week summary (week-of-month, Monday-based; W1 = week containing day 1)
  2026-10/W2/2026-10-08.md    day log — one section per session
~/bitacora/TOOLS.md           infrastructure shared by several projects
~/bitacora/INDEX.md           every project at a glance + what needs attention (generated)
```

Paths for the current session come from the SessionStart context, or `python <skill>/scripts/bitacora.py where`.

**Versioning & sync:** the bitácora lives in `bitacora/` of the private `metodologia` repo (with the skill in
`skill/`). Session end, web answers/approvals, round posts and launches commit automatically (only the bitácora
folder) and push in the background; SessionStart and every new ID pull first, so several machines stay in sync.
If the start context warns that sync failed, tell the user; nothing is lost locally. Changes to the skill itself
are normal commits. A new machine: clone the repo and run `python ~/metodologia/install.py`.
**Never run `git add -A` / `git commit -a` inside `~/bitacora`**: it's a folder of the monorepo, so that would sweep the
skill's work in progress into a log commit. Commit the bitácora only with `bitacora.py commit "<msg>"` (scoped to
bitacora/); a pre-commit guard in the repo rejects commits that mix bitacora/ with other files.

**Trace graph:** `bitacora.py trace` builds a graph from the IDs (REQ, US, R, T, D, P), the commits that cite them
(`Refs:` trailers) and the files those commits touched, and lints drift (requirements no task covers, tasks
covering unknown IDs, dangling or superseded references). `trace --bundle REQ-012` gives a compact linked context
for a handoff or a subagent brief; `trace --file <name>` answers "which requirements/decisions touched this file";
`trace --node REQ-012` lists its neighborhood. Run the lint before closing a requirement and when updating
central files. The web UI shows it as an interactive graph (project → Grafo) and per requirement (Trazabilidad).

**Web UI:** `bitacora.py web [--project X]` starts the local server (127.0.0.1:8765) if needed and opens it:
dashboard of projects, every document rendered, artifacts, question rounds and plan approval. It starts by itself
when a session opens in the HQ.

## Artifacts

When a visual page would help — a dashboard, a diagram, a comparison, a report, a UI mockup, a weekly summary
worth sharing — write it as a **self-contained HTML file** in `<project>/artifacts/<slug>.html` (inline CSS/JS; light
and dark friendly; small libraries from a CDN only if really needed). It's versioned with the bitácora and served at
`http://127.0.0.1:8765/p/<project>/view/<slug>.html`. Give the user that URL and log it in today's section.
Don't use any vendor-hosted artifact system for this skill's pages: they must work with any agent and stay in the
project's folder. Update an artifact by rewriting the same file (git keeps the history).

## The day log is the source

Each session has its own section in the day file, headed `## Session HH:MM · session `abcd1234``, created by the
SessionStart hook. Only edit **your** section — other sessions (maybe in parallel) own theirs.

| Subsection | What goes in |
|---|---|
| Goal | What this session set out to do (one line). |
| Done | Concrete outcomes, with paths/links (`src/x.py:42`, REQ-003, commit `1a2b3c`). Not activity ("worked on…"), results. |
| Decisions | One line each + its ID: `D-017 Use SQLite for the local cache`. The full entry lives in DECISIONS.md. |
| Not done (and why) | What was planned or attempted but not finished/dropped, and the reason (blocked by X, out of scope, deprioritized, failed because…). This is the part people forget and the most valuable later. |
| Pending | New or closed pending items by ID: `+ P-042 …`, `✓ P-031`. |
| Next session starts with | 1–3 concrete first actions. The SessionStart hook shows this to the next session. |

Keep bullets short. Prefer `file:line` references and IDs over pasted code.

## When to write

- **During the session, at the moment it happens:** a decision is made → DECISIONS.md + one line in the day log.
  A new pending item or problem appears → PENDING.md. A requirement is created or closes → day log. Don't batch
  this for the end; sessions end abruptly.
- **At the close of a piece of work / when the user wraps up** ("listo", "cerramos", "eso es todo", "documenta"):
  complete your session section, then propagate:
  1. DECISIONS.md / PENDING.md — anything not yet there.
  2. SUMMARY.md — rewrite *Current state*, *Active focus*, *Top pending*, *Recent decisions* if they changed.
  3. ARCHITECTURE.md — if components, data, integrations or flows changed.
  4. WEEK.md — rewrite this week's summary from its day logs (short).
  5. `python <skill>/scripts/bitacora.py index`.
- **The Stop hook** will block your stop and remind you if you changed files (or talked a lot) since the last
  bitácora update. When it fires, do the update — briefly. If truly nothing is worth logging, add a one-line note.
- **Before a long context gets compacted** (very long session), log proactively.

What's worth logging: decisions and their why, things finished, things dropped and why, problems found, pending
work, surprises/gotchas. Not worth it: routine reads, every command run, chatter.

## Central files — rules

**DECISIONS.md** — get the ID with `bitacora.py id D`. Entry format is in the file header. Append only; when a
decision changes, write a new entry with `Supersedes: D-xxx` and change only the old one's Status to
`Superseded by D-yyy`. A decision is anything a future reader would ask "why is it like this?" about: tech/library
choices, scope cuts, data model, process rules, trade-offs, rejected approaches.

**PENDING.md** — the project's backlog of deferred work, **ordered by urgency and complexity**. Get the ID with
`bitacora.py id P`, then add one line under `## Open`:
`- P-042 · Add retry to the SMS sender · urgency: high · complexity: S · added 2026-10-09 · antagonist REQ-003`
(detail lines indented under it travel with it). **Urgency** — high: hurts users/data/security or blocks work now;
med: should happen this cycle; low: nice to have. **Complexity** — S: under an hour, M: a session, L: needs its own
requirement. Always give both (estimate; don't leave `?`). You don't need to place it: `bitacora.py pending`
(also run at session start and end) sorts Open by urgency then complexity (urgent quick wins first) and moves items
whose title says DONE/FIXED/MERGED/CLOSED to `## Recently closed`. Blocked items go under `## Blocked`. Typical
sources: antagonist findings you deferred, out-of-scope ideas, Proposals the user didn't take yet, bugs found.

**SUMMARY.md** — rewritten, never appended. Someone reading only this file should know what the project is and
where it stands today.

**ARCHITECTURE.md** — the current truth, edited in place. History of *why* lives in DECISIONS.md. For business
projects, describe the process: actors, steps, systems, documents, handoffs.

## Rollups

- **Week:** WEEK.md is rewritten at each session close that week. When the SessionStart context lists past weeks
  under "Rollups due", finalize them: make sure the summary reflects all its day logs, set `status: final`.
- **Month:** same, built from its week summaries; also list pending items closed that month. Set `status: final`.
- Do rollups early in the session, quickly — they are a few minutes of reading, not a project.

## Bootstrap (new project)

When the SessionStart context says NEW PROJECT, the central files are empty templates. Fill SUMMARY.md and
ARCHITECTURE.md from what exists (README, code structure, configs, docs; or the user's description for a business
project). Keep it factual and short; mark unknowns as such. Log "bootstrapped bitácora" in today's session section.

## Projects are workspaces

A project is a **workspace**: a name plus one or more repos with roles, e.g. `maros` → `frontend: maros-next`,
`backend: maros-nest`. One bitácora, one set of requirements and one TOOLS.md per workspace, never per repo.
`bitacora.py --project <p> workspace add <role> <path>` registers a repo; `workspace show` lists them.

How a session finds its project, in order: the launcher's `BITACORA_PROJECT` → an explicit `bind` → the HQ folder
→ a `.bitacora` marker file → being inside a registered workspace repo → the git repo name (a repo nobody
registered becomes its own one-repo project, auto-registered).

The user usually works from the home folder, which spans every project. There the SessionStart context lists the
known workspaces: as soon as the request is clearly about one, run `bitacora.py bind <session_id> <project>`
(don't ask when it's obvious). If you forget, the Stop hook binds the session by the workspace repos it touched.
A new repo for an existing product → `workspace add` it, don't create a new project.
